My story

In September 2026 I joined the data team at BYU's Office of Information Technology as a Workday Developer. I was the newest member of a team that worked across every part of Workday, both HR and finance: reporting, integrations, data loads, exports and automations. I worked with Finance and HR stakeholders to turn what they needed into technical solutions.

The short version is in my story on the About page. This is the longer one.

My first assignment was a Workday Orchestration that had bugs. Instead of patching them, I rebuilt it to be simpler and faster, with stronger error handling. Then came my first big project: connecting Workday to the new software BYU's facilities department was adopting. That meant five integrations, each built from scratch.

The first lesson came from my lead. My first version of the hourly purchase order feed used prompts for the date range, and my lead pointed out that a scheduled feed has no one to answer them. That changed how I built. After that, I set dates with calculated fields so a feed could run with no one watching. On the same feed, I noticed each hourly run re-sent purchase orders it had already sent, so I changed it to send only what changed since the last completed run. The expense and invoice feeds worked the same way.

Part of the job was catching problems before they shipped. An outside Workday expert suggested a fix for a report that had to leave out contingent workers, and it worked on the two test cases. When I applied it to the real report, the output dropped from about 3,000 rows to about 300. Comparing the filters side by side, I found the fix removed every contingent worker, not just one subtype, which took out valid appointments like visiting faculty. I wrote up the root cause and a narrower fix instead, and the cut of about 90% never reached production.

I also built an orchestration from scratch in Workday Orchestrate that ran on its own whenever a candidate was hired, and fixed a bug in it once it was running in production. Then I designed a second one to set up supplier portal accounts automatically, a job the supplier support team had been doing by hand. Along the way I wrote a security troubleshooting guide for the team's shared workspace, and a Python script that handed older Workday cases off to Azure DevOps.

Monthly General Ledger Extract Across Fiscal Years

Pulls last month's journal lines every month and picks the right fiscal year on its own, even when last month belongs to the previous one.

Situation
The department needed the previous month's general ledger journal lines every month, through an EIB that would run with no one watching.
Task
Build the report and EIB from scratch so it always pulls the right month and fiscal year, with no one answering prompts.
Action
  • Built the journal lines report, with calculated fields for the first and last day of the previous month.
  • Hit a required Year prompt tied to today, which would pick the wrong fiscal year whenever last month fell in a different one. It expects a Fiscal Year instance, so no date or text field could fill it.
  • Ruled out the delivered defaults, none of which returns the prior fiscal year, and a Lookup Related Value workaround that added new required prompts.
  • Found a delivered default, Fiscal Year for Start Date and End Date, that reads two date prompts the report already had. Pointed both at a Date-typed chain for one month before today.
Result
The Year prompt followed last month's date instead of today, with a run across the fiscal year boundary as the final check.
Lesson
When a prompt can't be removed, look for a delivered default that reads inputs you can control.
  • Custom reports
  • EIB
  • Prompt defaults
  • Date calculated fields

Supplier Invoice Export with a Reconciliation Test Plan

A daily export of approved supplier invoice lines that let the facilities system close out purchase orders and record payments.

Situation
The facilities system used invoice data to mark purchase orders complete and record receipts and payments, so its totals had to reconcile to Workday.
Task
Build the integration from scratch and prove it works before go-live.
Action
  • Built the report on approved invoice lines, one row per line, with incremental logic that sends only lines that are new or changed since the last completed run.
  • Set up a daily 5 AM JSON delivery to cloud storage, with header and lines in a single file.
  • Wrote a 28-scenario test plan, with edge cases like 1-line and 250-line invoices, split lines, freight on the header or a line, punchout suppliers and invoices that span several purchase orders.
  • Added reconciliation checks (lines plus freight equal the invoice total, and unit cost × quantity equals the extended amount), and planned every test to run as the integration account, not an admin.
Result
One shared acceptance plan for business testers, the receiving system's support team and me before sign-off.
Lesson
Testing as an admin can hide a security gap that only appears when the integration account runs for real.
  • Custom reports
  • Incremental logic
  • EIB
  • JSON
  • Test planning

Sep 2026

Hourly Purchase Order Feed to an Asset System

An unattended feed that sent purchase order changes to the facilities asset management system every business hour.

Situation
The asset management system needed every new or changed purchase order from Workday, hourly from 7 AM to 5 PM, with no one watching the runs.
Task
Build the integration from scratch: a custom report matching an approved field mapping, its security, and an hourly delivery.
Action
  • Built the report on purchase order lines, using Lookup Related Value fields to bring header values like status and last-updated time onto each line.
  • My first version used prompts for the date window. My lead pointed out that a scheduled feed has no one to answer them, so I replaced them with calculated fields and made the one remaining prompt optional so it could never stop a run.
  • Fixed a datetime comparison alert by setting the calculated fields to the Moment type, to match the timestamp they compare against.
  • Noticed the “since midnight” window re-sent the same purchase order every hour, and moved to sending only what changed since the last completed run.
  • Wrote a 20-scenario test plan: incremental pickup, header-only and line-only changes, 1-line and 250-line orders, freight, status rules, rerun safety and delivery.
Result
A feed built to run every hour with no prompts to answer and to send each change once.
Lesson
A calculated field doesn't inherit the type of the field it's compared to, so set Date or Moment yourself.
  • Custom reports (RaaS)
  • Calculated fields
  • Integration system user
  • Cloud storage delivery

Purchasing Card Expense Feed

An hourly feed that sent approved purchasing card expenses to the same asset system, carrying only records that changed since the last run.

Situation
The asset system also needed purchasing card expense lines: approved, on one clearing project, approved in the last 30 days, and sent hourly from 7 AM to 5 PM.
Task
Build the integration from scratch, then migrate it to production and validate it end to end.
Action
  • Built the report to pick up a record when either the expense report or the line changed since the last run, and an EIB that writes it to cloud storage as JSON every hour.
  • Set both run-time inputs to the last completed integration event, in the integration and again in its schedule, which keeps its own copy.
  • Fixed a functional constraints error by giving the integration account's security group View access to the expense reporting domain, and a migration error by moving the pieces in dependency order: security, calculated fields, report, then EIB.
  • Traced a first scheduled run that failed in one second to having no earlier completed run to start from. A manual first run fixed it.
Result
Built, migrated and validated in production, and every scheduled run after the first succeeded. The business confirmed the incremental design matched what they intended.
Lesson
A new incremental integration needs one manual run to give the schedule a starting point.

  • Calculated fields
  • EIB
  • Launch parameters
  • Tenant migration

Daily Time Data Extract for Reconciliation

A daily extract of approved time data, delivered to a reconciliation platform before the workday started.

Situation
A reconciliation team needed the department's approved time data every day at 5 AM, delivered by SFTP with no one watching.
Task
Build the report and delivery from scratch, and make sure it was production-ready against the approved requirements.
Action
  • Built the report with the department's cost center hierarchy built in rather than prompted, filtered to approved, reported time blocks only so calculated rollup blocks stay out.
  • Set the date window with calculated fields and set up the daily SFTP delivery.
  • Before production, checked every filter and prompt default against the requirements doc, down to which boxes were actually checked. Found three fixes: an out-of-scope Worker prompt, a filter with no comparison value, and date defaults to confirm against the pay period requirement.
  • Flagged that the requirements doc was still in Draft, with its approvals and readiness checklist blank, and wrote a pre-migration checklist.
Result
Caught three configuration defects and an unsigned requirements doc before go-live.
Lesson
Check a build against the requirements' checked boxes, not just their visible text.

  • Calculated fields
  • Prompt defaults
  • SFTP delivery

Supplier Portal Account Provisioning

A planned boomerang orchestration, one that reads from Workday and writes back to it, that creates accounts for supplier contacts, emails their sign-in details and reports who hasn't signed in yet.

Situation
The supplier support team created portal accounts by hand, emailed a generic password and fielded reset calls. Tracking lived in a spreadsheet, with no record of when the email went out or whether the contact ever signed in.
Task
Design and build the orchestration from scratch, starting with requirements the business could sign off on.
Action
  • Turned the requirements meeting into recorded decisions: what triggers an account, how often it runs, and what waits for a later phase.
  • Designed the flow: an hourly run finds contacts flagged for portal access with no account, creates one, assigns the supplier contact role and emails a temporary password.
  • Wrote 16 functional and 6 email requirements, including a resume path for a run that creates the account but fails to send the email.
  • Built security into the design: a least-privilege security group, a forced password change at first sign-in, and no temporary password in any log, message or file.
  • Specified a daily report of outstanding sign-ons with five statuses, error handling with retries on the next run, acceptance criteria, and 13 open questions, with the 6 that block the build flagged.
Result
A requirements draft ready for stakeholder review, aimed at lower fraud risk, no manual password emails and fewer reset calls.
Lesson
Design for the partial failure. An account created with no email sent is the case that strands a user.
  • Workday Orchestrate
  • Account provisioning
  • Scheduled reports
  • Integration security

Complete · Sep 2026

Academic Appointment Filter and a Dual-Status Edge Case

A report filter that leaves out appointments tied to contingent workers, without dropping the appointments it should keep.

Situation
An integration needed academic appointments, minus those tied to contingent workers. The hard case was people who were an employee and a contingent worker at the same time.
Task
Build the report and its filters from scratch, including that edge case.
Action
  • Built the filters: primary academic appointment only, one excluded contingent worker subtype, faculty profile status and eligibility, and a trigger date. They worked for the general population, but dual-status workers still came through.
  • Tested a fix suggested by an outside Workday expert in a separate test report. It resolved the two known edge cases, but on the real report it dropped the output from about 3,000 rows to about 300.
  • Compared the two filter definitions side by side. The fix excluded every contingent worker, not just one subtype, so it removed valid appointments like visiting faculty. The reports' appointment sub-filters also checked different conditions, and the test report had only ever run on two hand-picked workers.
  • Wrote a case review that reframed the fix: target workers who are an active employee and a contingent worker at once, keep the narrow subtype exclusion, and validate on the full population.
Result
Stopped a fix that would have cut the report's output by about 90% from reaching production, and replaced it with a documented root cause and a precise next step.
Lesson
A fix that passes two test cases still has to be run against the full population.
  • Report filters
  • Sub-level filters
  • Calculated fields

Complete · Sep 2026

Least-Privilege Security for Integration Accounts

A repeatable way to give each integration's service account exactly the access it needs, and no more.

Situation
Every integration I built ran under its own integration system user and security group, set up from scratch. One account could own its report but couldn't be chosen as Run as System User when scheduling its EIB.
Task
Get each integration's security right with least privilege, and make the process repeatable for the team.
Action
  • Created a security group for each integration under the team's naming standard, with only the domains its report needed.
  • Traced the scheduling problem to the Integration Event domain, which governs launching and scheduling and is separate from Integration Build.
  • Found a second, independent check: per-integration security, which can lock an EIB to specific security groups whatever their domain access.
  • Wrote a five-step method (create the group, baseline the account's current groups, check report-level then field-level security, grant the domains, then check the data source), with a fallback of comparing against a similar integration that works.
Result
A reusable troubleshooting guide in the team's shared workspace, covering setup and the two most common security failures.
Lesson
Owning a report and running an integration are secured by different domains.
  • Integration system users
  • Security groups
  • Domain security

Complete

Case Handoff Automation Script

A Python script that handed older Workday cases off to Azure DevOps work items, told each requester where their work would continue, then closed and archived the case.

Situation
Older Workday cases already linked to Azure DevOps work items needed a consistent handoff, and requesters needed to know where their work would continue.
Task
Build a repeatable way to find eligible cases, notify requesters, and close and archive the cases, without repeating any step if the script runs again.
Action
  • Wrote a Python script that filters cases by configurable age, status, source and DevOps-link criteria, and checks that each linked work item exists before touching the case.
  • Made preview mode the default, so a run lists what it would do before changing anything.
  • Tracked each case's steps (email sent, case closed, case archived) in a local state database, so every step skips itself if it already happened and the script is safe to rerun.
Result
A configurable preview-then-process workflow, with separate tracking for notifications and closures.
Lesson
Default to preview and track every side effect, and a bulk script becomes safe to run twice.
  • Python
  • Azure DevOps
  • Local state database
